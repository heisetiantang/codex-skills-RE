# 饮食营养追踪（Diet Tracker）

用户报餐 → 逐项估算营养成分 → 记录进食时间 → 更新当日累计 → 输出汇总。全程维护一份可持久化的账本，用于跨天/跨周的趋势分析。**账本固定存于用户级目录（见持久化规则），跨工作区不丢失**。**首次使用时先做 5 秒画像确认（健康模式+体重）；确认前先按"通用中性默认基准"即时出结果，绝不因等画像而阻塞报餐**。

## 首次使用：初始化画像（Profile）

**触发时机**：按"账本定位"（见持久化规则）找不到既有账本时（首启），或用户明确说"重建账本/换个人设"。

**核心原则：先出结果，画像后补，5 秒确认，绝不阻塞。**
- 收到首条报餐时，**先按"通用中性默认基准"立即估算并输出**（基准表见下节）；
- 输出末尾**附带一行轻量确认**，只需用户回答 2 项：
  > 顺便定个基准：① 健康模式？控尿酸 / 通用 / 减脂；② 体重多少 kg？
- 用户回答 → 立即按画像重算达标基准并回写账本头部；用户不回 → 保持中性默认基准，下次报餐再问一次，不重复纠缠。

**信息收集（画像完整字段，供 5 秒确认后按需补齐）**：
1. 健康模式：`uric-acid`（控尿酸/痛风）/ `general`（通用）/ `weight-loss`（减脂）；默认按用户自述，自述尿酸高或痛风则取 `uric-acid`
2. 体重（kg）——蛋白/热量/水分基准的核心参数，**必问**
3. 性别 / 年龄 / 身高：用于 BMR 精算热量，能一句话带过就给（如"75kg 男 35 岁 175cm"），不便透露则用合理默认并注明"部分字段默认"
4. 饮食约束：素食 / 乳糖不耐 / 忌口（无则跳过）
5. 别名：单人使用默认 `main`；多人共用同一账本目录时，用别名区分各自账本文件

**画像生成**：把 profile 与计算出的达标基准写入账本头部（模板见 @references/ledger-template.md）。若用户没耐心/信息不足，直接采用下节"中性默认基准"并注明"未初始化，按默认基准"。

**画像/基准更新**（用户状态变了，不是报餐）：
- 触发词：用户说"我瘦了/胖了 Xkg""尿酸正常了""开始减脂了""改吃素了"等 → **不是普通报餐**，走更新流程
- 动作：重算达标基准 → 回写账本头部基准表 → 标注"按画像更新，X月X日"；当天的餐照常记录，不因基准变动重算历史
- 若用户只说"基准调一下"未给新数值 → 先问清变化量再算，别猜
- 更新后当次输出附一句：基准已从旧值调整为新值（列出变更项），让用户看到变化

## 工作流总览

每次收到报餐消息，按顺序执行：

0. **定位账本**：按"持久化规则"的定位顺序查账本（用户级 `~/.workbuddy/diet-ledger/` → 当前工作区历史遗留）——都没有 → 按"首次使用"处理：**先按中性默认基准估算本餐并输出，末尾附带一行 5 秒画像确认**；有 → 读取头部（画像+生效基准）后再继续
1. **逐项估算**该餐每种食物的营养成分（蛋白/脂肪/碳水/热量/水分/纤维）
2. **记录进食时间**与餐别（早/午/晚/加餐），能精确到 HH:MM 就记
3. **累加更新当日账本**（支持跨餐次增量；补报、纠错时只修正受影响的行）
4. **输出一张汇总表**（默认格式B 周视图，见展示规则），表后附 ≤3 行结论
5. 将最新账本**写入持久化文件**（见持久化规则）

用户要"按餐次明细""多天对比""周报告""完整分析报告"或"华为打卡清单"时，额外输出对应内容；**日常报餐后不主动附加大段建议**，只在结论行里点出当餐隐患与下一步补什么。

## 计算规则

### 估算优先级
1. **营养成分表实拍/官方数据** > 已验证食物库（@references/nutrition-guide.md）> 同品类近似估算
2. 有标签就按标签换算（每 100g/ml 值 × 实际克重），并在账本备注"成分表实测"
3. 复合菜品（小炒/外卖/食堂）按"主料可食部 + 烹调油"分别估算：肉按实际吃到的熟重估，油按烹饪方式估（清炒≈8~10g油/份、重油≈15~20g、油炸另计）
4. 估不准时明确标注"≈"或给区间，不要假装精确

### 每餐必算的 6 项
| 项目 | 说明 |
|------|------|
| 蛋白质 | 动物蛋白按 20~25g/100g 瘦肉、蛋 6.5g/个、奶 3~3.2g/100ml、豆腐 8~10g/100g 量级估算 |
| 脂肪 | 含烹调油；全脂奶 3.5~4.6g/100ml、脱脂 ≈0、瘦肉 5~10g/100g、五花 30g+/100g |
| 碳水 | 主食 25g/100g 熟饭、面条 26g/100g 熟、水果 12~25g/100g 不等 |
| 热量 | 由三大营养素推算或直接估算，单位 kcal |
| 水分 | 液体直接计 ml（奶/饮料/汤），食物含水不单列；**含咖啡因饮品（咖啡/浓茶）按杯量 60% 计入**（利尿损耗），并附一句"咖啡利尿，建议补 1:1 饮水"；无咖啡因（花草茶/代糖饮料）按 100% 计 |
| 纤维 | 蔬菜 1~2.6g/100g、豆类/毛豆 4~5g/100g、水果 2~3g/100g、坚果/奇亚籽密度高 |

完整常见食物速查与更多估算法见 **@references/nutrition-guide.md**（需要估某个不常见食物时读取）。

### 达标基准（先看画像，再看默认）

**生效顺序**：① 已初始化画像 → 用画像生成/用户自定义的区间；② 未初始化 → 用下表中性默认值（**对任何健康人群都不误伤**）；③ 用户随时口头改（"脂肪线放宽到60吧"）→ 立即覆盖并回写账本头部。

**中性默认基准（通用成人，未初始化时兜底）**：
| 指标 | 达标区间 | 判定 |
|------|---------|------|
| 蛋白质 | 55~75 g/天 | 55~75 达标；<55 偏低；>75 超标 |
| 脂肪 | ≤60 g/天 | ≤60 达标；>60 超标 |
| 热量 | 1500~2500 kcal/天 | 1500~2500 达标；<1500 偏低；>2500 超标 |
| 水分 | 2000~2500 ml/天 | 2000~2500 达标；<2000 偏低；>2500 仍算达标（多喝有益，不标红） |
| 纤维 | 25~30 g/天 | 25~30 达标；<25 偏低；>30 超标 |
> 中性默认故意放宽：未画像时只抓明显失衡，不误判；**拿到画像后必须收窄到个人线**。

**画像化基准的调整公式**（初始化后按 profile 重算这几项）：
- 蛋白质：`uric-acid` ≈ 体重kg×0.9~1.0；`general` ≈ ×1.0~1.2；`weight-loss` ≈ ×1.2~1.5（按 5 取整）。例：70kg 控尿酸 → 63~70 → 取 65~70g
- 热量：BMR = 10×体重kg + 6.25×身高cm − 5×年龄 + (男+5 / 女−161)；久坐维持 ≈ BMR×1.2；区间取 ≈维持×0.75 ~ 维持×1.1，并参考用户减脂/增肌目标微调，必要时让用户确认
- 水分：体重kg×30~35 ml/天；纤维：25~30g（成人通用）；脂肪上限：`uric-acid` 从严 ≤50g，其余 ≈ 热量上限×30%÷9
- 画像基准中的调整项须写回账本头部表格并注明"按画像生成，X月X日"

**尿酸人群附加规则**（仅当健康模式=`uric-acid` 时作为日常建议口径；`general`/`weight-loss` 不套用）：
- 肉类（红肉/禽肉合计）≤100g/天，忌海鲜、浓肉汤、内脏
- 忌含糖饮料、果味咖啡、鲜榨果汁（果糖升尿酸）；代糖饮料（无糖可乐等）可偶尔喝
- 奶选脱脂/低脂（全脂奶每天贡献 15~21g 脂肪）；鸡蛋、豆腐/豆浆低嘌呤放心吃
- 每天 2000ml+ 饮水帮助排尿酸；酒精（尤其啤酒）严格避免

## 记录规则

1. **每次报餐都要更新当日**：已吃的标"已吃"，建议的晚餐/加餐标"计划"或明确不纳入已摄入合计；用户只要求算"吃了的"时不混入计划
2. **进食时间**：记录餐次与具体时间（如 早08:20），用于后续节律分析（进食窗口/空腹时长）
3. **补报**：用户补报前几天漏掉的食物或饮水 → 定位对应日期行，累加并修正该日合计，重新输出汇总
4. **纠错**：用户纠正某道菜的真实做法/原料 → 只重算该行，更新当日合计，并在结论里说明变化
5. **同餐次冲突 → 先核对再记账**：同一日期同一餐次（如"早"）已有一笔记录、用户又报了一笔内容不同的 → 先展示已有记录，让用户三选一：`覆盖`（以新为准）/`追加`（两笔都算，新笔并入该餐）/`忽略`（保留原记录，新笔作废）；**用户未确认前不得静默覆盖或静默累加**。多设备/多窗口重复报餐极易触发此规则
6. **水分只入水分列**：饮水、牛奶、饮料等液体计入水分列，**不写进"吃了什么"列**
7. 用户可能随时要求只列出"已确认摄入"——此时不含任何计划内容

## 汇总展示规则

**默认输出格式B（周视图）**——每次报餐后只输出这一张表 + 三行结论：

- **当周**（本周一 ~ 今天）：**按天一行**
- **历史周**：**按周一行汇总**，5 个营养列取该周有记录天数的**日均值**，行内注明"周均·记N天"；所有历史周都必须列出（一行不漏）
  - **"周均"只在 N≥2 时使用**；某历史周只记录了 1 天 → 行内标"仅1天"，数值按当日原样显示，**不得冒充周均**
- 列顺序：`日期 | 蛋白 | 脂肪 | 热量 | 水分 | 纤维 | 吃了什么(时间)`，"吃了什么"放**最后一列**并标注进食时间
- 颜色（**字体颜色**，不用背景色）：
  - **绿色 = 达标**
  - **红色 = 偏低**（低于下限）
  - **深紫色 = 超标**（超上限）
  - 水分 >2500ml 仍标绿（多喝是好事）
  - Markdown 表格显示不了字体颜色时，改用带色 HTML/渲染表格输出，并提示用户
- "吃了什么"列：不写饮水；一餐一行放不下用分号紧凑罗列；不吃不换行
- 表后附**三行以内结论**：用 ✅ 标达标项、⚠️ 标短板/隐患，必要时一句具体下一步行动

**格式A（按餐次明细）**：默认**不展示**，仅在用户索要时给出——按 早/中/晚/加餐 分行，含每餐营养成分与进食时间，每天一行小计。

**简易报告（三行结论）模板**：
```
✅ [今日/本周做对的 1~2 点，可引用数字]
⚠️ [最需要补的 1~2 项缺口 + 一句话建议做法]
⚠️ [红线提醒（肉类超限/果糖/酒精/油脂）或明天注意点]
```

**周期报告**（用户要"分析报告/总结这几周"时）：见 @references/report-templates.md 的"精简诊断版"结构——突出 做得好 / 做得不好 / 怎么改 三块，避免罗列。

## 华为健康打卡清单（可选能力）

用户要"华为打卡清单"时，按当天账本输出**按餐别**的录入表：`餐别(时段) | 食物 | 热量 | 蛋白 | 脂肪 | 碳水`。规则：
- 每行一份食物，给出可直接照抄的自定义数值；0 热量的无糖饮料可标"可不录"
- 提示哪些食物需在 App 新建自定义、哪些食物库已有；复合套餐建议建成"整份"自定义一次点完
- 说明华为自定义食物只统计 热量/蛋白/脂肪/碳水，水分与纤维以本账本为准

## 持久化规则

**账本主文件固定于用户级目录 `~/.workbuddy/diet-ledger/`**（跨工作区共享，任何会话/任何工作区都读写同一份，避免"账本漂移"）。

**账本定位顺序**（每次报餐第一步）：
1. `~/.workbuddy/diet-ledger/MEMORY.md`（用户级主账本，默认位置）——存在且目录内**仅此一份** → 读取画像+基准后继续；目录内存在**多份**（多个 `<别名>-MEMORY.md`）→ 先按"多用户确认"问清归属再定位
2. 当前工作区 `.workbuddy/memory/MEMORY.md`（历史遗留账本）——存在但用户级没有 → **读取并迁移**：复制到 `~/.workbuddy/diet-ledger/MEMORY.md`，提示用户"旧账本已迁移"，之后一律以用户级为准
3. 两者都没有 → 按"首次使用：初始化画像"建账本，**新建即落在用户级目录**

**文件命名**：
- 默认单用户：`~/.workbuddy/diet-ledger/MEMORY.md`
- 多人共用同一台机器：每人一个 `<别名>-MEMORY.md`（别名来自画像，如 `xiaohua-MEMORY.md`），文件头注明 `Alias: xxx`
- **多用户确认**：`~/.workbuddy/diet-ledger/` 下存在**多个**账本文件时，收到报餐先确认归属："这餐记在谁账上？（小华 / 老张 / …）"，确认后再定位对应账本；**不确定时不默认 main**。只有目录里仅一份账本时才可直接使用
- 同一个人在**不同工作区**只维护用户级这一份，工作区内的 `.workbuddy/memory/` 不再作为主账本（迁移后旧文件可保留作备份，但不再读写）

**账本结构**：严格按 @references/ledger-template.md 的模板——头部（画像+生效基准+规则速记）→ 按日期分节的每餐明细与该日累计 → 底部"本账本实测沉淀"食物速查区。**账本内日期固定递增排列，最新一天始终追加在文件末尾**（不采用"最新在上"），便于续写与回溯

**初始化**：无现成账本时 → 先按"首次使用"给用户 5 秒确认画像，**无论用户是否回答都先按中性默认基准建账本并出结果**；用户随后补答 → 更新头部基准并注明日期

- 上传/同步到外部健康 App 不做任何自动化（华为等无个人 API），只提供手动录入清单

## 输出格式的通用原则

- 一切表格**精简、方便查看**；内容多宁可换行也不截断
- 数字能少写就少写：热量列不必带单位，表头注明即可；水用 ml
- 不做"企业客服式"铺垫，直接给表给结论
- 用户明确说"只需要…"时，严格只输出他要的那部分
